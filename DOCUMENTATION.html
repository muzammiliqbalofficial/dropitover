The problem it solves

Sending a file to a device sitting next to you is absurdly harder than it should be.

The usual options all cost something. Email caps attachments around 25 MB. WhatsApp compresses your photos and refuses large files. Cloud drives make you upload the whole file to a company's server, wait, share a link, then remember to delete it. AirDrop works beautifully and only between Apple devices. Existing web tools that promise to fix this tend to arrive with a free tier so thin it's a demo: a handful of files, ten megabytes each, deleted within the hour, with the actually-useful behaviour behind a subscription.

This project was built against that specific list. Each row below is a constraint it removes.

What it does

Three ways to send something, because "send a file" means three genuinely different situations.

Devices on your Wi-Fi

Mode 1 Nothing stored

Both devices are on the same network. Open the page on each one and they find each other automatically, like AirDrop. Tap a device, pick files, the other side accepts, and the transfer runs directly between the two browsers.

In every mode

  • Text and messages work, not just files.
  • Drag and drop, or tap to choose. Multiple files at once.
  • A progress bar for every transfer, in both directions.
  • Works on a phone. The layout, tap targets and inputs are built for it.
  • No account, no email address, nothing to install.

Where data lives

The single most important thing to understand about this project: two of the three modes never put your file on a server, and the third encrypts it before it lands.

ModeFile bytesWhat the server seesDeleted when
1 Same Wi-Fi Never stored Browser to browser Device names, connection setup messages Nothing to delete
2 Link Stored Encrypted in object storage File names, sizes, types, your message At expiry, or after download if chosen
3 Room Never stored Browser to browser Room id, display names, connection setup Room record expires after 12 hours

Why the server is involved at all in modes 1 and 3

Two browsers cannot find each other unaided. Something has to introduce them and pass along the technical details of how to connect. That introduction is all the server does here, and the messages it carries are capped at 128 KB precisely so the channel can never be quietly used to push a file through.

How each mode works internally

The mechanism behind each of the three, in order.

Mode 1 — finding devices on the same network

A browser cannot scan the local network, so discovery happens one level up. When a page connects, the server reads the public IP the connection arrived from, hashes it, and routes that connection to a small coordinator object dedicated to that hash. Every device behind the same router shares one public IP, so they all land in the same coordinator and see each other. Nobody else does. The raw IP is never stored or shown to anyone.

  1. Both devices connect and appear in each other's list within about a second.
  2. Tapping a device sends a request naming the files, count and total size.
  3. The receiver gets an accept or decline prompt before anything is negotiated.
  4. On accept, the two browsers exchange connection details through the server.
  5. A direct channel opens and the file streams across it in chunks.

Sending pauses automatically when the channel's buffer fills and resumes when it drains, and the receiver folds incoming pieces into storage every 16 MB. That is what keeps a 2 GB transfer from exhausting the browser's memory.

Mode 2 — the link share

This is the only path that persists anything, and it is built around a hard constraint: the code runs on Cloudflare's edge, where a single request body is limited to roughly 100 MB. A 2 GB upload therefore cannot be one request.

  1. The browser first sends a manifest: names, sizes, types, chosen expiry, burn flag.
  2. The server plans each file into fixed 8 MB pieces and generates the encryption parameters.
  3. The browser uploads pieces one at a time. Each is encrypted server-side before it reaches storage, so plaintext is never written.
  4. A finalize step seals the share and starts the expiry clock. Only then does the link resolve.
  5. Downloads run in reverse: pieces are read back in order, decrypted one at a time, and streamed out.

Chunking pays for itself twice. It makes multi-gigabyte uploads possible at all, and a failed piece retries on its own instead of restarting a two-gigabyte transfer.

Delete after first download

When enabled, the share is destroyed once everything has been collected, not after the first click. A share with four files survives until the fourth is downloaded. Deletion is also triggered by the last byte leaving, never mid-transfer, so the file cannot vanish out from under a download in progress.

Mode 3 — rooms

Creating a room mints a short id and a coordinator object that stores only when it was created and when it expires. Joining opens a connection to it; the object checks capacity and expiry, then hands the newcomer the list of people already inside.

One rule keeps the group connections orderly: the newcomer always initiates, and everyone already present answers. Without a rule like this, two browsers can call each other simultaneously and both connections collapse. Every join also extends the room's life by a full twelve hours, so refreshing the page or briefly losing signal never kills the link.

Cleanup

A scheduled job runs every ten minutes. It deletes shares whose time has run out, clears uploads abandoned more than an hour ago, and trims old rate-limit counters. Expiry is also checked on read, so an expired link stops working immediately rather than waiting for the next sweep.

Everything runs on Cloudflare's edge. There is no server to patch, no container, no always-on process.

One dependency

The entire application ships with a single runtime package, for drawing QR codes. Everything else — encryption, transfers, the interface, routing, storage — is written directly against the platform. Less to install, less to break, nothing to keep patched.

Security and privacy

Files kept on the server

Only Mode 2 stores anything. Every piece of every file is encrypted with AES-256-GCM inside the Worker before it reaches storage, so plaintext is never written to disk.

  • A separate key per file. Each file's key is derived from a master secret and its own random salt, so no two files share a key.
  • A separate initialisation vector per piece. Every 8 MB piece gets its own.
  • Order is authenticated. Each piece's position is bound into its encryption, so pieces cannot be reordered, duplicated or dropped without the decryption failing outright.
  • Tampering fails loudly. A single altered byte causes the download to error rather than return corrupt data. This is covered by a test.
  • The master secret lives outside the code. It is stored as a platform secret, never in the repository, and cannot be read back once set.

Transfers between browsers

Modes 1 and 3 use browser data channels, which are encrypted by the standard itself. Nothing is stored anywhere, so there is nothing to leak later. When a network makes a direct connection impossible and a relay is used instead, the traffic still stays encrypted end to end; the relay moves it without being able to read it.

What is deliberately not collected

  • No accounts, no email addresses, no passwords.
  • No analytics, no tracking, no third-party scripts. The page loads nothing from another domain.
  • IP addresses are hashed for grouping devices and for rate limiting, and are never stored raw or sent to any browser.
  • Device names are whatever you type. They stay in your own browser.

Abuse protection

Uploads are anonymous by design, which leaves storage as the one thing a stranger could run up. Each IP is allowed 10 shares and 5 GB per day. Going over returns a clear message and points at the peer-to-peer modes, which cost nothing to host and are never limited. If the counter itself ever fails, it deliberately allows the upload rather than taking sharing down with it — a quota is abuse control, not access control.

Testing

51 unit tests

  • Expiry: every time window, the exact instant a link dies, delete-after-download across multiple files, and the arithmetic for splitting a file into pieces — including a zero-byte file and a full 2 GB one.
  • Encryption: round trips, tamper detection, reorder detection, one file's key failing to open another's, and the wrong master key failing.
  • Rooms: joining, capacity, duplicate joins, leaving, lifetime extension, expiry.
  • Quotas: counting, per-IP isolation, daily reset, and failing open when the database is unreachable.
  • Relay credentials: response parsing and graceful degradation when the service is down.

41 checks against the live site

A separate script exercises the deployed app end to end: it uploads a 10 MB file in pieces, downloads it and compares it byte for byte against the original; opens two connections and walks through discovery, the accept prompt and the connection handshake; creates a room, joins from a second connection, and confirms both sides are notified; then deletes everything it made.

What tests cannot cover

The final hop — actual file bytes moving between two real browsers over a direct connection — needs two real devices and cannot be automated from a script. Everything leading up to it is verified; that last step is confirmed by hand.

Known limits

Things that are true about this build and worth knowing before relying on it.

  • Some networks block direct connections. Mobile carriers in particular. A relay service is configured to handle this, but on a badly behaved network a direct transfer can still fail. The interface says so plainly and points at link sharing, which always works.
  • Nearby discovery is by public IP, not true local networking. Browsers cannot scan a network. Devices behind the same router see each other; devices on different networks never will, by design. On some corporate or carrier networks that share one address across many customers, unrelated people could appear in the same list — which is why nothing sends without the receiver accepting first.
  • Per-IP limits are a speed bump, not a wall. They stop casual abuse and runaway scripts. They do not stop someone with many addresses.
  • The free plan allows 100,000 requests a day. Each 8 MB upload piece is one request, so a 2 GB file costs 256 of them. Comfortable for personal use, finite under load.
  • Losing the encryption key is unrecoverable. By design there is no way to read it back or reset it. If it is lost, stored shares are permanently unreadable.
  • Downloads assemble in browser memory. Very large files on a low-memory phone may struggle, since the browser holds the file as it arrives.
  • In-app browsers are restricted. Opening a link inside WhatsApp or Instagram blocks the features direct transfers need. The page detects this and tells the reader to open it in a real browser instead of failing silently.

How it got here

Two decisions shaped the code more than anything else, and both were reversals.

It was first built as a conventional Node server — Express, Socket.IO, files on disk. That version worked, with all three modes running. Then the target changed to Cloudflare, where none of it could run: Workers execute neither Express nor Socket.IO, and there is no filesystem to write to. The server was rewritten against the platform instead: hand-rolled WebSocket handling, coordinator objects in place of in-memory state, object storage in place of disk. The frontend survived almost intact. The original still sits in the project's history.

The 100 MB request limit forced the upload design. A 2 GB file cannot be one request at the edge. Rather than lower the promise to fit the platform, the upload was split into 8 MB pieces with encryption applied per piece. That single constraint is why the encryption is piece-based, why order is authenticated, and why a failed upload retries one piece instead of starting over.

The project was also renamed once. It shipped as ShareBeam until an existing site turned up under that name, so the name, logo and every user-facing word were replaced. The interface text was then rewritten a second time to strip out engineering vocabulary — protocol names and encryption jargon that told a visitor nothing about which button to press.
