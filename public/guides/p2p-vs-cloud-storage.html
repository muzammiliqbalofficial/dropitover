P2P versus cloud storage: compare the whole delivery workflow

Reviewed against the implementation: October 17, 2026

The useful question is not whether peer-to-peer or cloud storage is universally faster. It is which route fits the recipient's availability, network restrictions, file size, and trust requirements. DropItOver exposes both live WebRTC transfers and temporary server-stored links, making the tradeoff visible in one interface. A direct path avoids storing a reusable file on our server, while a link lets the sender finish before the recipient arrives. This guide compares those workflows using explicit assumptions, explains the different memory constraints, and provides a measurement procedure instead of presenting invented product benchmarks.

Map the data paths

Live direct: sender browser ===== WebRTC SCTP/DTLS ===== receiver browser
Live relay: sender ===== TURN carrying encrypted packets ===== receiver
Stored link: sender -> HTTPS Worker encrypts -> R2 -> Worker decrypts -> receiver

Peer-to-peer describes the live application relationship, but ICE may select a TURN relay rather than a local direct route. That relay still carries traffic and can be limited by internet bandwidth. A stored link has two separate transfers and server storage between them. In DropItOver, the Worker holds the encryption key and processes plaintext, so link encryption at rest does not exclude the operator from the trust boundary. A cloud product with client-held keys may have a different model; compare actual key ownership rather than treating every stored service as identical.

Availability changes the right answer

Use live transfer when both parties can keep browsers open and respond to acceptance prompts. It works well for a meeting, a quick device handoff, or a room session. Use a link when the recipient is asleep, traveling, or unable to stay connected. Select an expiry that leaves time for retrieval; a one-hour link sent across time zones can expire before anyone sees it. A room invitation is not an offline inbox and does not convert the mesh into persistent storage. Each participant needs a live connection to exchange file payloads.

Nearby discovery also has a separate dependency: browsers are grouped by their public IP at a WebSocket signaling service. A VPN or cellular connection can change that group. An explicit room avoids relying on the nearby list, but it does not remove firewall or client-isolation constraints. When a corporate environment forbids internet storage, the fact that an HTTPS link succeeds is not permission to use it. Select an approved route and consult the administrator before changing network policy.

Compare payload time with the same units

For one GiB, the payload contains 8,589,934,592 bits. A direct transfer's ideal payload time is those bits divided by the achieved end-to-end payload rate. A sequential stored workflow adds upload time and download time. The slow sender uplink often dominates, but local wireless contention can also make a direct path slow. Rates printed by a router or speed-test service are not necessarily the sustained rate your file receives. State whether MB means decimal megabytes or MiB means binary mebibytes when publishing a result.

These are arithmetic examples, not measurements of DropItOver, Snapdrop, LocalSend, or a cloud vendor. Real timing includes negotiation, request overhead, encryption, retries, saving, and background activity. Some stored services overlap processing or support different download behavior; this table specifically assumes upload completes before download starts. Do not quote its values as real-world rankings. If someone publishes a universal speed table without devices, network topology, file size, and timing boundaries, there is not enough information to reproduce or trust the comparison.

Memory and bandwidth are different resources

DropItOver's WebRTC sender pauses around an eight MiB data-channel queue and reads file slices. The receiver batches buffers into Blob parts but retains the complete received object for saving. That can consume browser-managed memory or disk resources proportional to the file. A sixteen MiB assembly threshold is not a promise of sixteen MiB total memory. Phones can exhaust resources even when both network and encryption are working. Test progressively larger non-sensitive files rather than jumping straight to the largest valuable archive.

The link Worker processes default eight MiB parts, but input, ciphertext, stream queues, and runtime overhead can coexist. Browser saving also has its own resource behavior. The current defaults cap stored files at two GiB each and bundles at eight GiB, with daily anonymous quotas. A direct path does not make hardware limits disappear. Compare peak process memory using the same tool and sampling method, and report what the number includes. A single protocol buffer constant cannot substitute for a measured memory result.

Troubleshoot the chosen path

For live transfers, separate discovery, acceptance, ICE setup, payload delivery, and saving. On Windows 11, review the active network profile and browser firewall permission without disabling the firewall. On guest Wi-Fi, test a trusted main network or personal hotspot to identify AP Isolation. On iOS Safari, keep the tab visible and screen awake. If a small document works but a large file fails, investigate resource pressure and suspension. A room may still require TURN; repeatedly creating rooms does not alter a blocked transport policy.

For stored links, inspect creation limits, upload completion, finalization, expiry, and recipient download as separate stages. Do not hand over a pending upload as though it were ready. Choose burn-after-read only when one retrieval of the complete share matches your needs. Encrypted download range resumption is not implemented here, so unstable connections may require a restart. Keep the source, verify the saved copy, and delete the stored share early only after the intended recipient has confirmed success.

Build your own fair comparison

Prepare one small fixture and one representative large file. Record OS and browser versions, device models, network arrangement, VPN state, relay status, and free storage. Run each method three times, keeping the file and timing boundaries fixed. Report median setup, payload, and saving times separately. For Snapdrop, record the deployment because configurations differ; for LocalSend, record app version and LAN conditions. Verify byte count and digest after every run so an incomplete transfer cannot win a speed test.

Choose based on the result that matters: time until the sender can leave, time until the recipient has a verified file, or the privacy and retention boundary your work requires. Those are different outcomes. Keep a concise record of the method that worked in your environment, and revisit it after meaningful browser or network changes. The related encryption and large-file guides explain storage keys, expiry, and retry limits in more detail. Support reports should include the failed stage and safe diagnostics, without disclosing private URLs or file contents.
