AES-256-GCM in DropItOver: keys, chunks, and trust boundaries

Reviewed against the implementation: October 17, 2026

Encryption claims are useful only when they identify who holds the key and where plaintext exists. DropItOver uses two different models. Nearby and room file payloads travel through browser-to-browser WebRTC data channels protected by DTLS. Link files arrive over HTTPS at a Worker, which encrypts them with AES-256-GCM before writing ciphertext to R2. The Worker also decrypts downloads. Calling both paths zero-knowledge would hide an important difference. This guide describes the implemented link format, the surrounding metadata, and practical steps for handling sensitive files without treating an algorithm name as a complete security guarantee.

Follow plaintext through the system

Sender file -- HTTPS --> Worker plaintext -- AES-GCM --> R2 ciphertext
Recipient <-- HTTPS -- Worker plaintext <-- AES-GCM -- R2 ciphertext
D1: names, sizes, salts, IVs, expiry, owner token, notes, object metadata

TLS protects the client-to-Worker connection. AES-GCM protects each stored file part and detects modifications under the relevant key. The Worker is inside the trust boundary because it possesses the master key and processes plaintext. Protecting an R2 object does not hide information in D1: file names, sizes, MIME types, and notes are stored separately. The operator or infrastructure controlling Worker execution is not cryptographically excluded. For a confidentiality requirement that excludes the service operator, encrypt the file independently before selecting it, or use an appropriate verified end-to-end system.

What AES-GCM authenticates

AES is the block cipher and GCM combines counter-mode encryption with authentication. It uses a Galois-field authentication construction, not Poly1305. In this application the tag is sixteen bytes and the IV is twelve bytes. Decryption must verify the tag; modified ciphertext, the wrong key, the wrong IV, or incorrect associated data causes authentication failure. This is stronger than simply obscuring bytes, but it does not stop an authorized recipient from copying the plaintext or an attacker with access to the running Worker from reading it.

An authenticated chunk is not automatically a signed document from a named person. The application relies on HTTPS, owner tokens, link secrecy, and its metadata database to select the expected share and part order. When handling a contract or release artifact, validate its signature or independently supplied hash if those are part of your workflow. AES-GCM transport and storage protections do not prove that a selected file was authored by a particular organization, that it is safe to execute, or that its contents are correct.

Keys, salts, IVs, and associated data

The server's MASTER_KEY is a 256-bit root key encoded as sixty-four hexadecimal characters. A per-file random salt feeds HKDF-SHA256 to derive a file key. Each file is split into default eight MiB parts, and each part has its own random ninety-six-bit IV. The part index is authenticated as associated data. The database records the salts and IVs needed to decrypt. These values are not substitutes for the master secret. Losing the master key makes stored link files unreadable; rotating it without a migration strategy has the same consequence.

The essential GCM rule is to avoid IV reuse with the same key. Random IV generation reduces collision probability; it is not a mathematical promise that randomness can never repeat. The implementation creates new per-file key material and per-part IVs rather than deriving an IV from an untrusted filename. Do not copy an example IV into production code. If changing retries or encryption internals, check that repeated requests cannot encrypt different plaintext under the same file key and IV. The repository's encryption tests exercise round trips and tampering detection, not every operational key-management failure.

Encryption does not eliminate retention questions

Links stop resolving after their selected expiry. A scheduled cleanup runs every ten minutes to delete expired data and abandoned uploads; an operational failure can delay physical deletion. Burn-after-read removes a completed share after all required items have been collected, while the sender can delete earlier using the owner token. These operations delete stored records and objects. They do not overwrite every physical storage sector, destroy a distinct hardware key for each share, or revoke copies already saved by recipients. Describe deletion accurately rather than promising instantaneous cryptographic shredding.

Direct WebRTC transfers avoid this stored file path, but signaling still exchanges identities, offers, SDP, and ICE candidates. TURN can carry the DTLS-encrypted traffic. The service is therefore not absent from every network exchange. Browser-delivered application code is also part of the trust model: compromised code can alter behavior before encryption or after decryption. Use the canonical HTTPS address and a browser you maintain, and verify the intended recipient out of band for high-consequence transfers.

Test correctness before discussing speed

For an implementation change, encrypt known non-sensitive bytes, decrypt them with the expected file key and part index, and compare every byte. Flip one ciphertext bit and confirm decryption fails. Try a different part index and a wrong key. Keep these tests separate from performance runs so a fast but incorrect implementation cannot look successful. Never use production master keys or real personal documents in a benchmark fixture. Avoid printing keys, private share URLs, or plaintext into test logs.

This table is format arithmetic, not an encryption-speed benchmark. Runtime memory can exceed one part because encryption input, output, network buffers, and stream queues coexist. To measure, report Worker configuration, file size, elapsed upload and download time, and the observation method. Browser-to-browser WebRTC and LocalSend use different transport paths; an AES-GCM microbenchmark cannot rank whole products. Hardware acceleration and implementation choices vary, so avoid claiming universal near-zero encryption cost on every phone.

Practical checklist for a sensitive transfer

Confirm the recipient and minimize the selection. Use independent file encryption if operator access is outside your acceptable threat model. Put any separately agreed password or key in a different communication channel. Choose an expiry with enough retrieval time, keep the original, and verify the saved copy. Do not include sensitive information in the filename or note unless you accept their storage behavior. After confirmation, delete the share if appropriate. Consult the Privacy Policy and the Web Crypto specification for the precise boundaries; an algorithm label is only one part of the full workflow.
