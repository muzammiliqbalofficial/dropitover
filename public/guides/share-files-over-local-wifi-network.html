Local Wi-Fi file sharing: discovery, isolation, and the actual data path

Reviewed against the implementation: October 17, 2026

Being connected to Wi-Fi does not necessarily mean two devices can communicate directly. Guest isolation, separate VLANs, VPNs, and the access point's forwarding policy can separate clients that both browse the internet successfully. DropItOver adds another distinction: nearby discovery groups browsers using a hashed public IP, while WebRTC independently finds a route for file data. Understanding those two layers prevents wasted troubleshooting. This guide shows how to test each layer on a network you control, choose an approved fallback on managed networks, and measure actual file delivery instead of relying on a router's advertised link speed.

Draw your network before changing it

Write down where each device connects: main SSID, guest SSID, Ethernet switch, phone hotspot, VPN, or cellular. Two identical Wi-Fi names can belong to different isolated segments, and different access points can still belong to one usable LAN. A mesh system may add another wireless hop between clients. A VPN may send signaling through a separate public IP even when local routing remains possible. Record the actual arrangement first; otherwise switching networks, firewall settings, and browser versions at once makes a successful retry hard to interpret.

Discovery: Browser A -> internet WebSocket -> hashed-IP hub <- Browser B
Transport: Browser A -> local route, NAT route, or TURN relay -> Browser B
Storage fallback: Browser A -> HTTPS Worker/R2 -> Browser B later

The discovery service is internet-based. Opening the already loaded page after disconnecting the router from the internet is not a supported offline discovery workflow. A successful nearby peer list establishes that browsers reached the same signaling group; it does not certify a private subnet, trusted identity, or direct file path. In environments where many people share one public address, confirm the receiving nickname and acceptance prompt carefully. If discovery grouping is unsuitable, use an explicit room and protect its invitation URL.

Establish a baseline transfer

Use two devices on a trusted main network with current browsers. Turn off only an unnecessary VPN that you are allowed to disable, and keep both pages visible. Set recognizable names, send one harmless document, accept on the other device, and save the received file. Record whether the offer appeared and whether payload bytes started moving. That baseline separates a basic connectivity failure from a later problem caused by file size, battery policy, or browser memory. Keep the original until the saved copy opens correctly.

If discovery is empty, verify each browser can fetch the page and configuration. Compare whether both devices actually use the same internet egress; a phone can silently switch to cellular when Wi-Fi appears unhealthy. An explicit room can bring together browsers with different public IPs. It cannot guarantee direct connectivity through a hostile router. When a room joins but files do not move, inspect ICE or test a trusted hotspot rather than repeatedly renaming devices. Device names do not affect packet routing.

AP and Client Isolation

Guest networks commonly permit each station to reach the gateway and internet while blocking station-to-station traffic. Settings may be named AP Isolation, Client Isolation, wireless isolation, guest separation, or a vendor-specific equivalent. On your own router, consult the model's documentation and move both devices to the trusted main SSID before changing policy. Do not disable isolation for an entire venue because one transfer failed. On a school or company network, ask the administrator for an approved local segment, relay path, or storage route.

TURN can relay DTLS-encrypted WebRTC traffic when it is configured and reachable. A relay is not equivalent to a guaranteed local path, and throughput may be constrained by internet uplinks or service limits. If you must keep bytes within a LAN, inspect the selected candidate pair and use a tool designed for your required offline conditions. If internet storage is acceptable, a temporary link avoids the peer route entirely. The right fallback depends on policy and trust requirements, not merely on which button happens to succeed.

Windows profiles and mobile foreground execution

On Windows 11, inspect the active connection under Settings, Network & internet. Private is appropriate for a trusted home network, while Public applies tighter defaults. Review the browser's firewall permission for the active profile; do not enable SMB sharing or open file-server ports for this browser workflow. Third-party endpoint protection can impose its own restrictions. A transfer working from the same PC on another trusted network is useful evidence when asking an administrator to review the original path.

On iOS Safari and Android, keep the tab foregrounded and screen awake during a live transfer. Power saving and app switching can stop application progress even though the Wi-Fi indicator stays visible. The receiving browser assembles a complete Blob, so large files also create resource pressure. Reducing the selection can distinguish memory limits from routing: if a tiny document succeeds consistently and a one GiB file fails, investigate resources and suspension before adjusting isolation. There is no persistent live-transfer resume state after a browser reload.

Use a troubleshooting matrix

TestWhat it establishesWhat it does not prove
Both pages loadOrdinary web accessPeer packet forwarding
Devices appearShared signaling groupSame subnet or trusted identity
Offer acceptedSignaling exchange worksSuccessful ICE route
Payload bytes increaseData channel carries trafficLocal rather than relayed route
Saved digest matchesCorrect selected file arrivedSender identity or document safety

Move through this matrix in order. Save the failed stage and the one change that improved it. Browser WebRTC reports can identify candidate types and connection state, but may reveal private network information. Redact raw addresses and session descriptions before sharing them publicly. A support ticket usually needs versions, network layout, file size, and state transitions rather than complete diagnostic dumps. Keep a record of changed router settings so you can restore the original security policy after testing.

Measure local performance reproducibly

Use a known one GiB file and run three trials per arrangement: both devices wireless, one wired, and a relay route if available. Report the median, not the best attempt. Keep devices, browser versions, file bytes, and timing boundaries consistent. A five GHz association rate is a physical-link property shared with overhead and other traffic; it is not application throughput. When two wireless clients share airtime, moving a laptop to Ethernet may help, but it cannot overcome a slow phone or policy block.

These are calculated examples, not observed results for DropItOver, Snapdrop, or LocalSend. Compare products only with the same devices and recorded route. Measure memory separately, because an eight MiB send threshold is not a whole-process ceiling and receive Blob storage scales with file size. Keep the original, verify the saved copy, and document the network arrangement that actually worked. That repeatable procedure is more valuable than a universal claim that local sharing is always instant or never touches a relay.
