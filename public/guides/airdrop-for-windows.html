AirDrop for Windows: a practical browser transfer workflow

Reviewed against the implementation: October 17, 2026

AirDrop does not provide a Windows receiver. If your sender is an iPhone and your destination is a Windows laptop, opening the Apple sharing sheet and waiting for that laptop will not create compatibility. Use a transfer method both devices actually support. This guide walks through DropItOver in two browsers, explains the Windows network settings that can interfere, and helps you decide when a temporary link or an installed local utility is the better fit. Start with an ordinary photo rather than your only copy of an important project.

Choose the path before changing Windows settings

Nearby devices is convenient when both browsers use the same trusted home network. A room gives you an explicit invitation when discovery lists differ. A link lets a recipient download after you leave. These are separate data paths, not progressively stronger versions of one connection. A room still needs a working WebRTC path, potentially through TURN; link sharing uploads data to our Worker and storage. Keep this distinction in mind when a corporate firewall allows web pages but blocks peer traffic.

First successful transfer, step by step

Open https://dropitover.com on the PC in an up-to-date browser. Open the same address on the phone, outside embedded social-media browsers. Give each device an identifiable nickname. On the PC, select the phone only after checking its displayed name with the person holding it. Choose a small file; on the phone, inspect and accept the offer. Keep both tabs visible until completion, then save the received item. Check the saved file's name, size, and ability to open before deleting anything from the sender.

Discovery uses a WebSocket service that groups browsers by hashed public IP. It does not enumerate Windows file shares, send Bluetooth advertisements, or scan your private subnet. Windows Network Discovery being off therefore does not automatically explain an empty browser list. A phone using cellular data, a laptop using a VPN, or a guest SSID with separate internet egress can land in a different group. Compare the network arrangement first. If both devices have ordinary internet access, an explicit room avoids dependence on the nearby list, while still requiring a working data connection.

Windows 11 Public versus Private network profiles

Open Settings, Network & internet, then the properties of the active Wi-Fi or Ethernet connection. Check whether Windows classifies it as Public or Private. A Private profile is appropriate only for a network you trust; do not change a hotel or airport network simply to make a transfer work. Managed devices may lock this setting. Browser WebRTC is not the same as Windows SMB sharing, so enabling file and printer sharing or exposing port 445 is unnecessary for this workflow and increases unrelated exposure.

If the browser has been denied access by a firewall product, review its application rules under the active profile. Allow the browser only as narrowly as your administrator permits. Test another trusted network to distinguish an endpoint rule from a router restriction. Do not disable Defender Firewall globally. If a security product blocks UDP, a configured TURN service with an allowed transport may help, but an ordinary HTTPS link is often the simplest permitted route. Record which change helped, then restore any temporary diagnostic exception that was unnecessary.

When the phone appears but the transfer stalls

Seeing a peer proves signaling works; it does not prove the local router forwards packets between clients. Guest Wi-Fi often permits internet access while blocking station-to-station traffic. Look for AP Isolation, Client Isolation, or a guest-network separation setting in your own router. Move both devices onto a trusted main SSID or your own hotspot before editing router settings. On an office network, ask the administrator for an approved transfer path rather than trying to evade isolation. A TURN relay can carry encrypted traffic if configured and reachable, but its use is not guaranteed.

Keep the iPhone unlocked and Safari in the foreground. Switching to another app, locking the screen, or activating aggressive power saving may suspend transfer work. On the Windows side, prevent sleep temporarily and keep the receiving tab open. A browser download prompt can also be hidden behind another window. If a large file repeatedly fails after a small one succeeds, investigate memory and background suspension before blaming discovery. Preserve the original file and retry a smaller selection. This implementation does not resume a partly received WebRTC file after a reload.

A performance worksheet you can reproduce

Use one 256 MiB test file and one 1 GiB file on the same devices. Run three transfers for each size, record elapsed time from acceptance to received completion, then verify the saved byte count. Use the median rather than the best run. Record browser versions, whether the PC is wired, the Wi-Fi band, VPN state, and whether ICE chose a relay. A wired laptop can improve a test by removing one wireless hop, but it does not bypass client isolation or create extra phone bandwidth.

These examples divide payload bits by an assumed rate and exclude setup, contention, and saving time. They cannot rank DropItOver against Snapdrop or LocalSend. Browser receivers may retain resources proportional to the whole file even though sending uses small chunks and an eight MiB backpressure threshold. Stop if Windows or the phone becomes unresponsive. A synthetic speed claim without the network path and device details is not useful evidence for your own transfer.

Picking an alternative and reporting a problem

Choose LocalSend when installed applications and local operation fit the environment; choose a browser when installation is inconvenient; choose a link when the receiver will be offline. For Apple-only pairs, AirDrop may be simpler. None of these options changes your organization's data-handling rules. Before requesting help, write down whether the peer appeared, whether the offer arrived, whether acceptance completed, and whether bytes began moving. Those four observations isolate discovery, signaling, connection setup, and file delivery far better than saying that the whole site did not work.

For technical references, consult Microsoft's Windows network-profile and firewall documentation, the WebRTC standard, and LocalSend's published protocol. Product behavior changes, so repeat a small-file test after browser or operating-system updates. Our related WebRTC and sensitive-document guides explain the transport and trust boundaries in greater depth. When contacting support, provide a redacted screenshot and device versions; do not paste private file contents or a live download URL into a public report.
