How DropItOver transfers files over WebRTC

Reviewed against the implementation: October 17, 2026

A browser file-transfer tool has two distinct conversations: instructions that arrange a connection, and the stream that carries the selected bytes. Confusing them makes failures hard to diagnose and privacy claims hard to evaluate. DropItOver uses WebSockets for signaling and WebRTC data channels for nearby and room transfers. Temporary links use a different HTTPS storage path. This walkthrough follows the actual implementation, identifies where memory grows, and gives you a repeatable way to investigate a connection without assuming that a successful page load guarantees a successful file transfer.

Discovery and signaling do not carry the file

On the homepage, the browser opens /ws/net. The Worker hashes the connecting public IP and selects a NetworkHub Durable Object. Browsers in that group exchange identities and receive a peer list. The sender selects a peer and sends a transfer offer containing a summary; the recipient accepts or declines. Only then do browsers negotiate their data channel. This means connection metadata, including file names in offers, can pass through signaling even though the file payload does not. Confirm the intended recipient rather than treating a nickname as identity proof.

Sender ---- identity / offer / SDP / ICE ---- Signaling ---- Receiver
Sender ========= SCTP messages inside DTLS encryption ===== Receiver
                                 direct route OR TURN relay

In a room, the room identifier selects a different Durable Object. A newcomer initiates connections to existing members, while existing members answer. That rule avoids both ends always creating simultaneous offers. It also means a group is a mesh: sending a file to several recipients creates several deliveries, not one server broadcast. A participant with a slow radio can finish later than everyone else. Room membership, data-channel readiness, and transfer completion should therefore be considered separate states when diagnosing group behavior.

ICE chooses a reachable route

An RTCPeerConnection gathers candidates representing possible transport paths. STUN helps discover a public-facing address; it does not normally forward file bytes. TURN provides relay candidates when a direct route cannot be established. Browsers exchange candidates through signaling, then perform connectivity checks. A working WebSocket tells you the browser can reach the signaling service, not that UDP between peers or a TURN endpoint is allowed. Symmetric NAT, guest isolation, VPNs, and managed firewalls can alter which candidate pair succeeds.

Use the browser's WebRTC diagnostics or getStats() to inspect the selected candidate pair. A relay candidate indicates a TURN path. A host candidate may indicate a local address, but browsers can obscure addresses with mDNS, and a candidate label alone is not a throughput measurement. Record whether the pair becomes nominated and whether bytesSent and bytesReceived increase. Keep diagnostics private: SDP and candidate reports may reveal addresses and network details. A redacted state transition is usually enough for a support request.

SCTP messages, DTLS, and backpressure

The data channel transports ordered application messages over SCTP protected by DTLS. This is file data, not a media stream, so describing its payload protection as SRTP is inaccurate. DropItOver sends a file-start JSON message, binary slices, and a file-end message. The sender chooses a slice size using the negotiated SCTP maximum message size, with an application ceiling of 256 KiB. If a peer advertises an unexpectedly small limit, compatibility needs investigation; the application should never assume every browser accepts arbitrarily large messages.

The sender pauses when the channel's bufferedAmount reaches about eight MiB and resumes after the browser reports that the queue has drained toward one MiB. This is backpressure: it prevents JavaScript from reading the entire source file into an ever-growing send queue. It does not reserve eight MiB for the entire process or promise that operating-system memory will remain flat. Browser networking, encryption, file slices, and receive storage all allocate additional resources. A progress bar reports application delivery, not a universal statement about disk persistence or integrity.

Receive memory is a separate constraint

BlobAssembler groups received buffers into Blob parts around sixteen MiB. The final Blob still represents the whole received file. Browsers may place backing storage in memory or on disk depending on their implementation and resource pressure. Consequently, a two GiB file can fail on a phone even when the send queue is bounded. Closing the tab discards application state. There is no persistent WebRTC resume journal here; keep the source and restart after an interrupted transfer. A file-end message triggers assembly and the browser's save workflow.

For important transfers, compare the final byte count and, when feasible, a SHA-256 digest generated independently on both devices. A digest mismatch means the saved copy is not the expected file, regardless of whether a UI says complete. DTLS protects the active transport, but it cannot tell you whether the sender selected the correct document or whether an operating-system export produced a different media version. A saved filename is helpful context, not a cryptographic identity.

On Windows 11, review the active network profile and browser firewall rule, without turning off the firewall. On a router you control, check guest isolation; on someone else's network, use an approved alternative. On iOS, keep Safari foregrounded and the screen awake. Change one variable at a time and record the result. Randomly changing the router, browser, and VPN together can hide which restriction caused the problem and make the next failure impossible to reproduce.

Measure transport without inventing benchmarks

Create a known one GiB file, note both browser versions, and run three direct transfers, followed by three relay transfers if a relay is available. Record setup time separately from payload time. Do the same with a sequential link upload and download. Compare median payload throughput in MiB per second, not the Wi-Fi association speed printed by the operating system. The latter includes radio capacity that other clients and protocol overhead also consume. Use browser process measurements consistently if comparing memory.

These are arithmetic scenarios, not observed rankings or promises. Snapdrop also uses browser peer transport, while LocalSend uses a different local application protocol; neither can be assigned a speed from its product name. Consult the W3C WebRTC specification for data-channel semantics and the projects' published source for comparison details. If documenting a result, publish the chosen route, file size, timing method, repeat count, and memory measurement method alongside the numbers so another person can repeat the experiment.
