WebRTC signaling, STUN, and TURN: diagnose the failing stage

Reviewed against the implementation: October 17, 2026

Signaling, STUN, and TURN do different jobs. A signaling service introduces browsers and relays connection descriptions. STUN helps a browser learn a public-facing address. TURN offers a relay path when direct connectivity is unavailable. Treating all three as a generic server makes troubleshooting imprecise and can produce misleading claims about whether file bytes touch infrastructure. This guide maps each role to DropItOver's implementation, shows what a successful stage proves, and explains how to test restrictive networks without exposing private diagnostics or disabling security controls broadly.

Signaling is the control conversation

The homepage opens /ws/net and joins a NetworkHub selected from a hash of the request's public IP. Room pages use /ws/room with the room identifier. The Durable Object relays identities, offers, responses, SDP, and ICE candidates. The file payload uses a separate data channel after acceptance and negotiation. Consequently, an empty nearby list can be a discovery-group problem even when a room would work, and a visible peer can still be unreachable for data. File names and sizes in transfer offers are metadata, not evidence that signaling stores the complete file.

1. Browser -> WebSocket signaling -> peer list and accepted offer
2. Browser -> STUN -> public-facing candidate information
3. Both browsers exchange ICE candidates through signaling
4. ICE checks choose direct path OR TURN relay
5. SCTP over DTLS carries file messages on the selected path

Signaling needs ordinary internet reachability to the Worker. A loaded static page does not prove that a WebSocket upgrade succeeded. Some enterprise proxies permit HTTPS documents but block or interfere with WebSockets. On passive disconnect, the client reconnects with backoff rather than showing a raw HTTP status in the page. Active transfers can still fail and should produce actionable feedback. A reconnected signaling socket is not a persistent file-resume mechanism; do not assume an interrupted received file continues after reload.

STUN discovers an address; it does not guarantee reachability

NAT can map a private client to an external address and port. A STUN exchange reveals information the browser can propose as a server-reflexive candidate. Whether another peer can use that candidate depends on both networks' mapping and filtering behavior. Carrier-grade NAT, symmetric mapping, restrictive firewalls, and isolated Wi-Fi clients can prevent a direct route. STUN responding successfully is therefore an intermediate observation, not a successful end-to-end connection or proof that a file will stay on the local network.

Browsers can also offer host candidates, sometimes with mDNS-obfuscated names. Do not treat an unfamiliar candidate address as an error solely because it is not a visible private IP. ICE gathers and checks several possibilities. The selected candidate pair, its state, and growing byte counters matter more than the presence of one candidate in a log. Candidate reports can reveal network details, so redact them before public sharing. A connection-state timeline often supplies enough information for support without publishing the full SDP.

TURN relays the encrypted transport

If a usable relay candidate is available, traffic can pass through TURN instead of requiring a successful direct route. The file data remains protected by browser-to-browser DTLS, while the relay carries encrypted packets and can observe operational connection information. TURN bandwidth may be metered and constrained by network paths. It is inaccurate both to say TURN never handles traffic and to say it automatically decrypts file contents. It is also inaccurate to promise a relay can bypass every policy: its endpoints and offered transports still have to be reachable.

DropItOver can mint short-lived Cloudflare TURN credentials when the appropriate key ID and API token are configured. Static TURN configuration is another supported deployment option. The configuration endpoint falls back to STUN when credential minting fails, keeping the page usable but potentially leaving restrictive network pairs unable to connect. A badge or config response showing no relay is a useful diagnostic. Do not expose long-lived service secrets to clients or paste credential API tokens into a support ticket. Inspect the selected candidate pair

Use getStats() or your browser's WebRTC diagnostics to find the active transport and nominated candidate pair. Record connection state, candidate types, timestamps, and whether byte counters increase after acceptance. A relay candidate indicates TURN usage. Keep setup time separate from payload time. The existence of many failed candidate checks is not itself a failure if another pair succeeds. Conversely, one successful WebSocket ping says nothing about the data channel's traffic. Describe the stage you actually observed rather than collapsing every symptom into server downtime.

For a controlled test, compare two devices on a trusted LAN, then test one on cellular, and finally a relay-capable arrangement if available. Do not assume the cellular test must succeed without TURN; NAT behavior varies. Run a small harmless file before a large one and save the copy. If the PC uses a VPN, record whether turning it off within policy changes discovery, route selection, or both. Each result answers a different question, so change one variable at a time.

Restrictive networks and mobile execution

On Windows 11, inspect Public versus Private profile and browser application permissions without disabling the firewall. On a router you control, check guest or client isolation; on a managed network, ask the administrator for an approved path. An explicit room changes how peers meet, not the underlying firewall rules. A temporary link uses HTTPS storage and may be appropriate when peer routing fails, subject to data-handling policy. Do not present a technical fallback as authorization to bypass an organization's storage restrictions.

On iOS Safari, keep the tab foregrounded and screen awake. A successful ICE connection can still stop making application progress when a page is suspended. Large receives can also strain memory because the browser retains the completed file as a Blob representation. Those are not STUN failures. If a small transfer works repeatedly while large ones fail after app switching, investigate execution and resources before changing relay credentials. Retain the source, since live partial delivery is not persisted across reloads.

Support reports should identify the failed stage and safe state information, leaving private addresses, tokens, documents, and live download links out of public logs.
