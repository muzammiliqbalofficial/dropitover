Send large files without email: limits, retries, and verification

Reviewed against the implementation: October 17, 2026

Email is convenient for a short note, but a large video or archive usually needs a different delivery method. DropItOver offers live browser transfers and temporary download links. Choosing between them depends on whether both people can stay online, whether the network permits peer traffic, and whether server-managed storage is acceptable for the material. This guide explains the limits in the current configuration, how chunked link uploads work, and how to verify a received copy. Do not delete the source merely because a progress bar has moved to its final stage.

Pick live delivery or a stored link

A nearby transfer or room sends file payloads over WebRTC while both browsers remain active. A TURN relay may help traverse restrictive networks, but a room does not create an offline inbox. Link sharing uploads to the Worker and R2 so the recipient can arrive later. That path processes plaintext in the Worker, encrypts file chunks for storage, and decrypts them for authorized downloads. It is server-managed encryption at rest, not a client-held secret that makes the operator unable to read the content.

The defaults limit link files to 2,147,483,648 bytes each and a bundle to 8,589,934,592 bytes. Those are two and eight GiB, even where UI labels use GB. Anonymous link creation is also limited by daily share and byte quotas. The server checks declared sizes and enforces part sizes during upload. A filename ending in ZIP does not change the number of bytes counted. If a large selection exceeds the quota, do not repeatedly retry creation; use a suitable direct method or wait for the stated reset.

Preparing a large selection

Check free disk space on both ends, especially if you create an archive before sending. Archives help preserve directory structure and reduce repeated download prompts, but many video and image formats are already compressed. Compressing them again may consume time without reducing size. If you intentionally split an archive, explain how to reassemble it and ensure every part arrives. The service does not split an over-limit file into separately named downloads for you. Keep the original and the archive until the recipient confirms a usable copy.

Select an expiry that covers upload time, the recipient's expected arrival, and a reasonable retry window. Burn-after-read is appropriate for a known recipient who will retrieve the whole bundle once; it is inconvenient when several people need their own copy. Treat the download URL as a bearer secret. Anyone who receives it can attempt access while it remains valid. Share it through an appropriate channel and avoid putting private URLs into public issue trackers, analytics examples, or screenshots.

What chunking changes and what it does not

Manifest -> reserve link -> upload 8 MiB parts -> finalize -> usable URL
Each part: HTTPS plaintext to Worker -> AES-GCM -> R2 ciphertext
Download: R2 part -> Worker authenticates/decrypts -> HTTPS recipient

Default eight MiB parts remain below typical proxy request-size limits and let failed pieces retry individually. Multi-part R2 uploads are completed only after the application finalizes the share. Before finalization, an in-progress upload is not a ready download. Chunking reduces per-request work; it does not make total bandwidth free or guarantee survival of a closed browser tab. There is no cross-reload upload session recovery UI. If the sender disappears before completion, abandoned uploads are later removed by the scheduled cleanup process.

During download, the Worker decrypts and streams one part at a time. Authentication verifies each part before release. The endpoint does not support ordinary HTTP range resumption, so an interrupted download may need to start over. Prefer a stable connection and sufficient battery when receiving a large bundle. A transfer's expiry can also matter during a long session: starting seconds before expiration is a poor plan. Ask the sender for a fresh link if the original is close to its deadline or was deleted after a previous retrieval.

Common failure patterns

  • Creation rejected: inspect the file cap, bundle cap, message size, and daily quota before retrying.
  • Upload stops on mobile: keep the tab foregrounded, avoid screen lock, and test a smaller non-sensitive file.
  • Recipient sees an expired link: check selected duration and whether the sender deleted or burned it.
  • Download restarts after disconnection: range resume is not implemented for this encrypted stream.
  • Saved archive will not open: compare byte count and digest, and confirm every split archive part arrived.

On Windows, Public versus Private profile settings matter mainly to local peer traffic and application rules; they are not a reason to disable the firewall for an HTTPS upload. On a guest router, AP Isolation can block nearby WebRTC while the link route still works. On iOS Safari, foreground execution remains important during uploading. These observations help choose a route instead of repeatedly changing unrelated network options. If your organization's policy forbids cloud storage, an otherwise convenient link is still the wrong choice.

Estimate time before promising a deadline

For a sequential upload-then-download workflow, add both legs. One GiB contains about 8.59 gigabits. Divide that by the sender's payload upload rate and then by the receiver's payload download rate, and add the results. This is an ideal payload estimate; setup, encryption work, other users, retries, and file saving increase elapsed time. Wi-Fi marketing rates are not measured application throughput. Test with a representative file and record three runs if timing matters.

To compare methods fairly, use the same devices and bytes, label direct versus relay paths, and include saving time separately. Watch receiving-browser memory for live transfers: building Blob parts still retains a representation of the entire file. A storage-based route and a direct route have different memory behavior; a single chunk size is not a peak-process-memory measurement.

Confirm delivery and clean up

Ask the recipient to open the saved copy, compare byte size, and calculate an independent digest for important archives. Once they confirm success, use the owner's delete control when early deletion is appropriate. Expiry blocks later access and the scheduled sweeper removes stored objects, normally on a ten-minute cycle; it cannot erase recipient copies. A useful support report includes the failed stage, file sizes, mode, browser, and approximate time. Keep the private owner token and download URL out of public reports, and retain the source until the issue is resolved.
