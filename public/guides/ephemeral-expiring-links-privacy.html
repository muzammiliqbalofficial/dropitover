Expiring file links: access deadlines, deletion, and recipient copies

Reviewed against the implementation: October 17, 2026

An expiring link is a temporary access mechanism, not a way to control a file after someone saves it. DropItOver lets a sender choose a link lifetime, delete a share early, and optionally remove it after completed retrieval. Those controls reduce how long the service offers the stored copy, but they do not erase recipient downloads, screenshots, forwarded attachments, or independent backups. This guide follows the share lifecycle in the implementation and explains the difference between an access deadline, scheduled cleanup, and a verified handoff. Keep that distinction explicit whenever you use a timer as part of a privacy workflow.

Follow the share lifecycle

A link begins as a pending upload. The browser submits file metadata and expiry preferences, receives upload details and an owner token, and sends file parts. The Worker encrypts parts with AES-256-GCM before R2 storage. Finalization completes the upload and makes the share ready; the expiry clock for a completed share is tied to that lifecycle rather than a public promise that any selected file is instantly available. Do not distribute a link until the interface confirms completion, especially when the upload is large or the sender's connection is unstable.

pending -> parts uploaded -> finalized / ready -> accessible until expiresAt
                                         -> sender delete
                                         -> completed burn-after-read
expired or abandoned -> scheduled object and metadata cleanup

The defaults offer one hour, six hours, twenty-four hours, three days, or seven days. Choose enough time for the recipient's schedule, not merely for the upload. A person in another time zone may not see a short-lived URL before it expires. If the material needs recurring access, an expiring share may be the wrong primary record. Use a controlled document or storage system for that purpose rather than treating a temporary download address as permanent infrastructure.

Access expiry and physical cleanup are separate

Once the expiry condition is reached, the application treats the share as unavailable. The scheduled sweeper runs every ten minutes to remove expired shares, associated file records, objects, and abandoned upload state. A delay between access expiry and object cleanup is therefore expected. An operational failure can extend that delay. A privacy statement should describe this design instead of promising that a storage object is overwritten at the exact millisecond shown on a countdown timer. Check monitoring and cleanup behavior when operating the service.

The Worker manages the master encryption key and derived file keys, so deletion is not the destruction of an independent hardware secret per share. Ciphertext lives in R2 while metadata, notes, salts, and IVs live in D1. The running Worker sees plaintext during encryption and decryption. Short retention reduces exposure time but does not make this stored path zero-knowledge. If excluding operator access matters, independently encrypt the selected file before uploading and exchange its key using a suitable separate process.

Owner controls and bearer links

The download URL is a bearer capability: whoever receives it can attempt access while it is valid. The owner token authorizes management actions such as upload completion and deletion. Keep these values private and do not paste them into public bug reports. A recipient should not need the owner's management token. If you distribute a link through a channel with many viewers, the service cannot infer which person was intended merely from the address they opened. Confirm the recipient through an existing trusted channel before sending sensitive material.

Use the sender's delete control after the recipient verifies a saved copy if early removal fits the task. Do not delete while someone is still downloading and expect an uninterrupted result. If you lose the private owner state, avoid assuming you can recover management access from the public URL alone. Contact support for applicable help without publishing the secret. The safest ordinary routine is to keep the source, wait for recipient confirmation, remove unnecessary server availability, and retain records according to your own policy.

Burn-after-read is a bundle rule

A share can contain several files and a note. Removing everything after the first file click would lose the rest of the bundle, so completion needs to account for all required items. The implementation tracks retrieval and deletes once the required files and note have been collected. Explain this to recipients and avoid using the option when several people need independent copies. Opening a preview and deciding to retrieve the remainder later may be awkward in a one-retrieval workflow, particularly if the connection is unreliable.

A download reaching the service's completion condition is not a guarantee that a person deliberately saved and reviewed every item. Browser saving, local disk errors, and user choices remain outside the server's knowledge. For a critical handoff, ask the recipient to confirm the saved copy explicitly. If burn-after-read has already removed the share and the recipient needs another attempt, create a fresh share from the retained source. Expiring URLs are designed to become unavailable, so keep another recoverable copy until the handoff is finished.

Reliability still depends on the transfer path

The link route uses ordinary HTTPS, but uploads can stop when mobile browsers are suspended or the network drops. Keep the tab active until finalization. Downloads stream decrypted parts and do not implement ordinary range resumption, so an interrupted large download may restart. Nearby and room modes are alternatives for live delivery, but depend on WebRTC routing and foreground tabs. Guest isolation or a Windows application firewall can block those paths even when link uploads work. Choose the mode deliberately rather than equating expiration with reliability.

For testing, use harmless files with a short selected expiry. Confirm the share is available before its deadline and unavailable afterward. Exercise early deletion and a complete multi-file burn share separately. Do not test deletion against someone else's active production transfer. Record whether the UI, API state, and stored records agree, and use authenticated administration for storage inspection. A public endpoint should not expose database rows or owner tokens merely to make a cleanup test easier.

These are arithmetic examples, not measured benchmarks for DropItOver or competing tools. Measure your actual upload, finalization, download, and saving stages separately, and run repeated trials if timing matters. Memory is also separate: part processing reduces per-operation payload size but does not cap all runtime allocations, and live browser receives retain a full Blob representation. A countdown timer should include realistic operational margin. If a share behaves unexpectedly, provide support with the mode, approximate time, safe size details, and failure stage rather than a private file, owner token, or working confidential link.
